# Source issues: errata, ambiguities and environment differences

The transcripts are the primary source of truth for **what** this system teaches. Where a statement in them turned out to be wrong when **executed**, this system teaches the verified behavior and links back here.
Covers all seven transcripts (lecture0-lecture6). Verification environment: SQLite 3.45.1, MariaDB 10.11 (stands in for MySQL), PostgreSQL 16. The tests in `tests/test_system.py::test_errata_claims` re-run the SQLite checks, and `tests/test_servers.py` re-runs the server checks.

| # | Where | What the lecture says | What actually happens (verified) | Impact on this system |
|---|---|---|---|---|
| 1 | lecture2 L1335-1347 | A column declared with no type gets **NUMERIC** affinity. | It gets **BLOB** affinity (also called "no affinity"): `CREATE TABLE t(x); INSERT INTO t VALUES ('10');` gives `typeof(x) = 'text'`. A NUMERIC column would give `'integer'`. | Lesson C2.5 and review item R2-08 teach BLOB affinity. |
| 2 | lecture3 L1077-1087 | With `AUTOINCREMENT`, SQLite reuses an unused id (e.g. 3). | **Reversed.** Without AUTOINCREMENT, SQLite uses max(id)+1, so after deleting the *highest* id, that id can come back. With AUTOINCREMENT, ids are **never** reused: after deleting id 3 (the max), the next id is 4. Neither mode fills gaps. | Lesson C3.1 and review R3-04. The part about the default (L1073-1076, "take the highest and add 1") is correct. |
| 3 | lecture2 L971-978 | `NOT NULL` on foreign-key columns is redundant, because the FK constraint already prevents NULL. | A foreign-key column **accepts NULL** (a NULL references nothing and is never checked). If a link is mandatory, add `NOT NULL` yourself. The PRIMARY KEY half of the claim is right for `INTEGER PRIMARY KEY`. | Lesson C2.7, debugging D2-03. |
| 4 | lecture2 L1311-1313 | "My foreign key constraints aren't actually being checked right now, but yours might be." | SQLite **does not enforce foreign keys by default**. Each connection must run `PRAGMA foreign_keys = ON;`. The lecture3 demo that raises a FOREIGN KEY error (L895) only works with it on. | Every practice database in this system runs `PRAGMA foreign_keys = ON`, and Lesson C3.6 explains it. |
| 5 | lecture3 L358, L1324 | Inserts accession number `06.1899` (spoken unquoted). | Unquoted, `06.1899` is a *number*. The TEXT affinity column stores `'6.1899'` and the leading zero is lost. Identifiers that look numeric should be inserted as quoted strings. | The seed data quotes them; review R3-09 asks you to predict this. |
| 6 | lecture4 L1136 | `create trigger delete ...` | `delete` is a keyword and must be quoted (`CREATE TRIGGER "delete" ...`). Otherwise the result is `near "delete": syntax error`. The lecture's on-screen code presumably quoted it. | Solutions name it `"delete"`. |
| 7 | lecture6 L659-668 | "decimal 5 comma 1 ... between -999.99 and 999.99". | `DECIMAL(5,2)` is ±999.99. `DECIMAL(5,1)` is ±9999.9 (MariaDB accepted 9999.9 into DECIMAL(5,1) and rejected 99999.9). The rule: M total digits, D of them after the point. | Lesson C6.2 and review R6-03 use the correct rule. |
| 8 | lecture6 L2124-2136 | The prepared statement "escapes" SQL keywords, so `1 UNION SELECT * FROM accounts` only runs the `= 1` part. | A prepared statement **never parses the value as SQL**. It is bound as data. MariaDB/MySQL then compares the INT id with the string `'1 UNION ...'` by converting it to a number (1), raising warning 1292 *Truncated incorrect DECIMAL value*. That is why Alice comes back. In SQLite, the same bound string matches **no** row (there is no numeric conversion). | Lesson C6.8 and exercise M6-E08 explain binding vs escaping. |
| 9 | lecture6 L564-574 | VARCHAR(300) uses up to 300 bytes for every short string. | VARCHAR stores the actual length plus 1-2 length bytes. It is **CHAR(M)** that always uses M characters. Over-sized VARCHARs still have costs (memory for temporary tables and sorts, weaker validation), so "size it thoughtfully" stays good advice. | Lesson C6.2 notes it. |
| 10 | lecture6 L787-797 | `MUL` in `DESCRIBE` means "foreign key / multiple". | `MUL` means the column is the first column of a **non-unique index**, so duplicate values are allowed. In InnoDB, foreign-key columns get such an index automatically, which is why they show MUL. | Lesson C6.2 explains it. |
| 11 | lecture4 L820-848 | "You can't update a view." | True **in SQLite** (verified: `cannot modify v because it is a view`) unless you add INSTEAD OF triggers. MySQL and PostgreSQL allow INSERT/UPDATE/DELETE through *simple* single-table views. | Lesson C4.8 makes it SQLite-specific. |
| 12 | lecture4 L324-330 | Put ORDER BY in the view and its rows are "saved" sorted. | SQLite does honor an ORDER BY inside a view, but standard SQL does not guarantee row order unless the **outer** query has ORDER BY. | Lesson C4.2 recommends ordering in the outer query. |
| 13 | lecture5 L475-476 | "search stars using the index ... called name_index given some person ID". | Slip of the tongue: that line of the plan uses **person_index**. | None |
| 14 | lecture3 L1618 | "create trigger sell before delete on transactions". | Misread on screen: the trigger is `BEFORE DELETE ON collections`. | None |
| 15 | lecture4 L1192 | "the ID column has been updated from a 0 now to a 1". | Slip: the **deleted** column changed. | None |
| 16 | lecture3 L929 | "DELETE FROM artists WHERE artist_id = ..." | The lecturer catches this at L947-953: it must be `DELETE FROM created`. | Used as debugging item D3-02. |
| 17 | lecture5 L1260-1325, L1536 | ROLLBACK / BEGIN EXCLUSIVE demos. | The behavior is correct. One note: in SQLite a failed statement inside a transaction does **not** automatically roll the transaction back. You must issue ROLLBACK (as the lecture does). | Lesson C5.7 |
| 18 | lecture3 L1000-1004 | `ON DELETE NO ACTION`: "I could delete the primary key referenced by this foreign key, and nothing would happen. I would actually be allowed to do that." | **Not allowed.** NO ACTION means "take no *special* action", but the foreign-key constraint is still checked. With `PRAGMA foreign_keys=ON`, SQLite fails with `FOREIGN KEY constraint failed`, and MariaDB with error 1451. The difference from RESTRICT is only timing: RESTRICT fails immediately, while NO ACTION is checked at the end of the statement (or transaction, if deferred). | Lesson C3.6 table. |
| 19 | lecture0 L1314-1325 | "MAX seems to give us the lowest alphabetically". | Slip: on text, `MAX` returns the alphabetically **last** value (*Wretchedness*), and `MIN` the first (*A New Name…*). The lecture's conclusion that MAX/MIN don't measure length is right. | Lesson C0.10, review R0-07. |
| 20 | lecture1 L1652-1662 | UNION / INTERSECT / EXCEPT need "the same number and the same type of columns … same column names". | Only the **number** of columns must match. The result takes its column names from the first SELECT, and SQLite does not enforce matching types (verified: `SELECT n AS first_name … UNION SELECT n AS other_name …` works). Matching kinds of data is still good practice. | Lesson C1.9, debugging D1-09. |
| 21 | lecture0 L951-971 | LIKE is case-insensitive. | True only for **ASCII** letters by default: `'A' LIKE 'a'` is 1, but `'Ñ' LIKE 'ñ'` is 0 (verified). | Lesson C0.7. |
| 22 | lecture0 L1363-1373 | A misspelled column `"pubsliher"` "creates this data for me". | The mechanism: SQLite treats a double-quoted identifier that matches no column as a **string literal** (a legacy misfeature). MySQL and PostgreSQL would report an unknown column. | Debugging D0-03. |
| 23 | lecture1 L1673-1677, lecture4 L374-384 | Slides: book 1 has ratings 4, 3, 4 (avg 3.67), and book 2 has 2, 3 (avg 2.5). | These are **illustrations**. The same lectures' real query outputs say book 1 has 2,779 ratings averaging 3.774… and book 2 has 176 averaging 3.97 (lecture1 L1737, L1799-1800; lecture4 L409). The datasets follow the real outputs. | Review R1-06, exercise M1-E19. |
| 24 | lecture0 L603-606 | "Or IS IT NULL, meaning that it actually is there." | Transcription: the operator is `IS NOT NULL`. | None |
| 25 | lecture1 L1349-1351 | "the first one's on the left; the first one's on the right". | Slip: for two joined tables, the first is on the left and the second on the right. | None |
| 26 | lecture1 L1213-1288 | RIGHT JOIN / FULL JOIN demonstrated. | Correct, but supported only since **SQLite 3.39.0** (2022). Older versions fail with "RIGHT and FULL OUTER JOINs are not currently supported". | Lesson C1.7. |

## Environment differences you will notice

* **Dataset size.** `movies` here is a small sample (19 movies), not the 400k-row IMDb file, so `.timer` differences are tiny. `python3 tools/build_db.py --big` adds 300,000 synthetic movies and people so the Lecture 5 timing demos become visible again. `EXPLAIN QUERY PLAN` output is the same at any size.
* **Ratings and votes are synthetic but engineered.** The individual ratings in `longlist` are generated so that the lectures' own query results come out the same: lecture1 L1685, L1737, L1769-1770, L1799-1800, and lecture4 L409, L581-586. The same applies to the ratings and votes in `longlist0` (lecture0 L1003, L1037-1075, L1166, L1243-1267, L1288). `tests/test_system.py::test_facts_from_the_lectures` checks them.
* **Publishers.** `longlist0` has 30 distinct publishers, while the lecture's data has 33 (lecture0 L1401). Three books' publishers were left unknown (NULL) rather than guessed.
* **MySQL → MariaDB.** Everything in Lecture 6 that this system executes ran on MariaDB 10.11. MariaDB's `DESCRIBE` output and some messages differ slightly from MySQL 8.
* **Plan wording.** SQLite ≥ 3.36 prints `SCAN movies` where older versions printed `SCAN TABLE movies`.
